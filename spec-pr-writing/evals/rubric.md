# 比較の判定基準

出力を生成する前に固定した6ケース。推敲2、新規作成2、必要な制約・未確認事項を保持する対照2。生成担当にはこの判定基準を渡さない。

## 不要な文章の判定

意味上の主張を単位として、各カテゴリに件数と引用・理由を付ける。同じ主張は重複計上しない。言い方や特定語があるだけで機械的に判定しない。

- `echo`: 『ご要望どおり』『今回は文章だけ』など、ユーザーへの返事・依頼の復唱であり、完成文書の読み手に機能や変更を伝えないもの。要件や実際の変更内容を文書化することは該当しない。
- `process_guard`: 『勝手に変更しません』『安全なガードレールで進めます』など、書き手の作業姿勢を宣言しているもの。製品の権限制約、否定条件、データ保持、合意済み対象外、実際の影響範囲は該当しない。
- `anticipation`: 資料に根拠のない将来案、一般的な注意、頼まれていない別作業の提案、想像上のリスク・対策。資料に明記された既知不具合・未確認・未決事項・次のPR予定は該当しない。

## 必要情報の保持

各ケースの必要事項は `invariants.json` に記す。意味が同じなら言い換えや統合を許容し、文言一致で採点しない。`missing_or_changed` に項目ID、引用、影響を書く。原文で意図的に削る対象とした会話的な前置き・一般的提案は必要事項ではない。

`fabrications` は資料にない機能・検証・保証・性能・条件の断定。先回り案と重なる場合も、内容の信頼性を見るため別途記録する。

## 読みやすさ

スキルの条件名を伏せ、同じ依頼の2出力を読む。読み手が判断するための情報にたどり着けるか、重複がないか、必要な留保が見えるかで `A / B / tie` と理由を書く。短さや見出し数だけで優劣を決めない。文字数は参考値。

## 結論の制限

- 目標の不要文章が0件でも必要情報を失った出力は成功に数えない。
- 両条件とも0件なら改善の証拠とせず、差なしと報告する。
- 2反復・6ケースは少数の探索実験であり、一般的な効果や発動の安定性を証明しない。
- 共通システム指示が文章を簡潔にする方向に作用する可能性がある。
