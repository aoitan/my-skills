# Implement TDD Flow Skill

このスキルは、`docs/CURRENT_PLAN.md` に定義されたタスクを一つずつ実行します。
**重要:** このスキルはコードの変更とテストの実行のみを行います。**Pull Requestの作成は行いません。**

## 前提条件 (Prerequisites)
- `docs/CURRENT_PLAN.md` が存在し、承認されていること。
- テスト実行環境が整っていること（例: `npm test`, `pytest` 等）。

## 思考・実行プロセス (Execution Process)

「実装して」と言われたら、計画書のタスクごとに以下の **TDD Cycle** を厳密に回してください。

### 1. The TDD Loop (Red -> Green -> Refactor)

計画書の各タスク（Step）に対し、以下の3段階を実行します。一度に全てのコードを書こうとせず、ステップごとに確認してください。

#### 🔴 Phase 1: Red (Test First)
1.  **Action**: 計画されている機能に対する**失敗するテスト**を作成してください。
2.  **Verification**: テストコマンドを実行し、**「想定通りの理由で失敗すること」**を確認してください。
    - *Check*: コンパイルエラーではなく、アサーションエラーで落ちているか？

#### 🟢 Phase 2: Green (Make it Pass)
1.  **Action**: テストを通すための**最小限のコード**を実装してください。
2.  **Constraint**: ここで過剰な機能追加や、計画にないリファクタリングをしないでください。
3.  **Verification**: テストを実行し、Green（成功）になることを確認してください。

#### 🔵 Phase 3: Refactor (Clean up)
1.  **Action**: 通ったテストを壊さないように、コードの可読性を上げたり重複を排除してください。
2.  **Constraint**: 動作ロジックを変えてはいけません。
3.  **Verification**: 再度テストを実行し、Greenのままであることを確認してください。

---

### 2. Implementation Check (Self-Correction)

全てのタスクが完了したら、以下を確認してください。

- [ ] 全てのテストが通過しているか？ (`Run all tests`)
- [ ] `docs/CURRENT_PLAN.md` の "In-Scope" を満たしているか？
- [ ] 計画にないファイル（"Non-Goals"）を変更していないか？

### 3. Human Review Request (Final Stop)

**ここがこのスキルのゴールです。**
PRを作成する前に、ユーザーにレビューを依頼してください。

以下のフォーマットで報告し、**処理を停止**してください。

```markdown
## ✅ 実装完了 (Implementation Complete)

TDDサイクルによる実装とテストが完了しました。

### 実施内容
- [x] テスト作成 (Red) -> 通過 (Green)
- [x] リファクタリング完了
- [x] 全テスト通過確認済み

### 変更ファイル一覧
- `src/...`
- `tests/...`

### 次のアクション
コードを確認してください。問題なければ **「PRを作成して」** と指示してください。
（修正が必要な場合は指示をください）
```

## 🛑 Scope Safety Rules (厳守事項)

このスキルを実行する際は、以下のルールに従ってください。自動フォーマッタやLinterとの競合を防ぐための例外規定を含みます。

1.  **Logic Strictness (ロジックは厳格に)**:
    - 機能的な変更（変数名変更、関数の移動、ロジック変更）は、`docs/CURRENT_PLAN.md` に記載されている範囲でのみ許可されます。
    - 計画にないリファクタリングは禁止です。

2.  **Style Tolerance (スタイルは寛容に)**:
    - **Exception**: 自動フォーマッタ（Prettier等）による空白、改行、クォートの変更は**許容してください**。これらを元に戻そうとしないでください。
    - 自分が変更していない箇所のフォーマットが変わっていても、それは「無視」してください。

3.  **Lint Fix Constraint (Lint修正の制限)**:
    - あなたが変更したコードブロック内で発生したLintエラーは修正してください。
    - **重要**: あなたが触っていない既存コードのLintエラー（以前からある警告など）を修正しようとしないでください。それは「別タスク」です。

4.  **Diff Check Strategy (差分確認のコツ)**:
    - 自分の変更を確認する際は、可能な限り `git diff -w` (空白無視) を使用し、本質的なロジック変更のみをチェックしてください。

5.  **Respect the Legacy**:
    - 既存のコードが汚くても、今回のタスクに関係なければ**そのまま維持**してください。
    - 修正が必要な場合は、コードを書き換えるのではなく、`TODO:` コメントを追加するだけに留めてください。

## 禁止事項 (Prohibitions)

1.  **PRの作成禁止**: `gh pr create` はこのスキルでは**絶対に実行しないでください**。それは別のスキルの責務です。
2.  **テスト無視の禁止**: テストを実行せずに「実装しました」と報告しないでください。必ず実行ログを確認してください。
3.  **計画外の修正**: ついでに気になった箇所の修正（Lintエラー修正など）は、計画に含まれていない限り行わないでください。
