# Architect Coding Plan Skill

このスキルは、ユーザーの要望やIssueの内容を分析し、**「何を実装し、何を実装しないか（Non-Goals）」**を明確にした実装計画書を作成します。

## 目的 (Objective)
- 実装の解像度を上げ、コーディングAgentの迷いをなくす。
- **スコープクリープ（範囲の肥大化）を防止する。**
- レビュー時の「正解基準」を事前に合意する。

## 入力コンテキスト (Input Context)
1.  **Issue/Request**: 実装したい機能やバグ修正の内容。
2.  **Codebase Context**: 関連する既存コード (`git ls-files`, `cat ...` 等で取得)。
3.  **Constraints**: 技術的制約（使用するライブラリ、パフォーマンス要件など）。

## 成果物フォーマット (Output Template)

計画は以下のMarkdown形式で作成し、ファイル（例: `docs/CURRENT_PLAN.md`）またはIssueコメントとして保存してください。

```markdown
# Implementation Plan: {Task Name}

## 1. 概要とゴール (Summary & Goal)
- **Must**: {必須要件}
- **Want**: {あれば良い要件 - 基本的に今回はスコープ外とする}

## 2. スコープ定義 (Scope Definition)
### ✅ In-Scope (やること)
- {具体的な実装項目}
- {変更するファイルパス}

### ⛔ Non-Goals (やらないこと/スコープ外)
- **リファクタリング**: 今回の変更に関係のない箇所のコード整理は行わない。
- **追加機能**: {関連しそうだが今回はやらない機能}
- **依存関係**: 新しいライブラリの追加は行わない（必要な場合は明記）。

## 3. 実装ステップ (Implementation Steps)
1.  [ ] **Step 1**: {詳細なタスク}
    - *Action*: `src/foo.ts` に `bar` 関数を追加。
    - *Validation*: 単体テスト `tests/foo.test.ts` を作成。
2.  [ ] **Step 2**: ...

## 4. 検証プラン (Verification Plan)
- どのテストが通れば完了とするか。
- 手動確認が必要な場合の手順。

## 5. ガードレール (Guardrails for Coding Agent)
- 既存のロジックを変更する場合は、必ずコメントで理由を残すこと。
- この計画に含まれないファイルの変更は禁止する。
```

## 思考プロセス (Thinking Process)

計画を立てる際は、以下の順序で検討してください。

1.  **要件の境界線を引く (Draw the Line)**
    - ユーザーの要望を実現するために「最小限必要な変更」は何か？
    - 触ると危険な箇所（レガシーコードや複雑な依存関係）はどこか？
2.  **既存コードとの整合性**
    - 既存のアーキテクチャ（設計パターン）に従っているか？
    - 新しいパターンを導入する必要があるか？（ある場合はその正当性を記述）
3.  **リスク評価**
    - この変更によって壊れる可能性のある機能は？

## 実行手順とスコープ維持のルール (Execution & Scope Management)

### Phase 1: 計画作成
1.  コンテキストを収集し、上記のテンプレートを埋める。
2.  **ユーザー承認**: 作成した計画をユーザーに提示し、承認を得る。「この計画以外は実施しない」ことの合意を取る。

### Phase 2: コーディング中の参照ルール (Instruction for Coding Phase)
後続のコーディング担当Agentには、以下の指示を与えてください。

> 「`docs/CURRENT_PLAN.md` の手順に従ってコードを書いてください。
> **重要:** この計画書に書かれていないファイル修正やリファクタリングは**厳禁**です。
> もし計画に不足がある場合は、勝手に進めず、計画の修正を提案してください。」

### Phase 3: レビュー修正ループ (Review Loop)
レビュー指摘が入った場合、以下の基準で判断してください。

- **バグ修正の場合**: 計画のタスクの一部として修正を行う。
- **仕様変更・改善提案の場合**:
    - それは `CURRENT_PLAN.md` の **In-Scope** に含まれるか？
    - **Noの場合**: 「今回のスコープ外（Out of Scope）として、別Issueに切り出す」ことをユーザーに提案する。
    - **Yesの場合**: 計画書を更新してから修正を行う。
