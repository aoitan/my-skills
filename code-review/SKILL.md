# 手順

ユーザーの要求から以下のパラメータを抽出し、レビューコマンドを実行してください。

- **Issue Number**: 指定があれば `-i` で渡す。文脈から明らかな場合も補完する。
- **Base Branch**: 比較元ブランチ。指定がなければ省略（デフォルトに任せる）するか、`-b` で指定する。
- **Spec**: 追加の仕様や指示。自由文のまま渡さず、以下の「レビュー制約テンプレート」に埋め込んで渡す。

## レビューモード判定（重要）

ユーザーの依頼内容から、以下のいずれかを判定する。

- **初回レビュー**
  - 例: 「レビューして」「厳しめに見て」
- **再レビュー（修正後確認）**
  - 例: 「修正したので再レビュー」「前回指摘の確認」「潰せたか見て」

再レビューと判断できる場合は、`Spec` に必ず「再レビュー用テンプレート」を適用する。

## レビュー制約テンプレート（初回レビュー用）

以下を `Spec` の先頭に追加してから、ユーザー指定の追加指示を後ろに連結する。

```md
- 差分レビューを優先する。差分に無関係な既存コードの新規探索は最小限にする。
- 指摘は「再現可能な不具合 / 要件違反 / セキュリティ / 重大な保守性問題」を優先する。
- スタイル・命名・好みベースの指摘は、ユーザーが明示的に求めた場合のみ行う。
- 出力は重要度順に、最大10件まで。
- 各指摘には、対象箇所・根拠・最小修正案を含める。
```

## レビュー制約テンプレート（再レビュー用・重要）

再レビューと判断できる場合、以下を `Spec` の先頭に追加してから、ユーザー指定の追加指示を後ろに連結する。

```
目的は「前回指摘の解消確認」と「今回差分で新たに入った重大問題のみの検出」です。

### スコープ
- 差分レビューのみを行う。
- 指摘対象は以下に限定する:
  1) 前回指摘の未解決・再発
  2) 今回の差分が直接原因の重大な不具合
- 以下は指摘しない:
  - スタイル/好み
  - 命名
  - 将来の改善提案
  - 差分に無関係な既存コードの問題
  - 前回「許容」または「見送り」と合意済みの事項

### 再指摘ルール
- 既出の指摘を表現だけ変えて再指摘しないこと。
- 新規指摘として出す場合は、既存IDと異なる具体的根拠（別の失敗モード/別経路）を示すこと。

### 終了条件
- 上記条件で問題がなければ `PASS` のみ返す。
- 問題がある場合のみ `FAIL` を返し、最大3件まで。

### 出力形式
- 先頭行に `PASS` または `FAIL`
- `FAIL` の場合、各指摘を以下の形式で出力:
  - [ID] severity: (critical|high|medium)
    scope: (prev_issue|new_from_diff)
    location: <file>:<line or line-range>
    issue: <具体的な問題>
    evidence: <なぜ問題か>
    minimal_fix: <最小修正案>
```

### 前回指摘台帳の扱い
- ユーザーが前回指摘台帳を提供した場合は、それを基準に解消確認する。
- 台帳がない場合は、新規レビューのように観点を増やさず、今回差分の重大問題のみに限定する。

## 実行コマンド

```bash
# PATHを通す
uv tool update-shell

# レビューコマンド
llm-review -i <issue_number> -b <base_branch> "<spec text>"
```

## 制約事項

- レビュアーの指名がない場合は --reviewers オプションを省略すること。
- ユーザーが「すべてのレビュアー」と言及した場合のみ --reviewers all を付与する。
- Spec は自由文をそのまま渡さず、必ず上記テンプレートを前置して渡すこと。
- 再レビュー時は、可能ならユーザーに「前回指摘台帳（ID付き）」の貼付を促す。
